1. What Makes This Solution Approach Unique?
While many teams build standard keyword RAG or basic fuzzy string matching, EntityIQ introduces four fundamental architectural innovations:
Pluggable Multi-Stage Entity Resolution Engine:
Stage 1 (Blocking): Generates high-speed index keys (Name Prefix, RegNo, Tax ID, LEI) to reduce search space from millions to candidate blocks.
Stage 2 (Deterministic Match): Evaluates high-confidence strict equality rules (REG_NO_EXACT, LEI_EXACT, DOC_HASH_EXACT).
Stage 3 (Probabilistic Feature Matrix): Calculates weighted similarity across multi-modal signals:
Jaro-Winkler string distance on company name variants and historical aliases.
Jaccard token overlap on registered office addresses.
Board of Directors overlap ratio.
Stage 4 (Decision Threshold Classifier):
: AUTO_LINK (automatically merged into canonical entity record).
: NEEDS_REVIEW (routed with explainability evidence logs to KYC Analyst).
: NO_MATCH (creates a distinct candidate entity).
GraphRAG + Leiden Community Aggregation:
Document RAG alone misses corporate relationships. EntityIQ applies Leiden Community Detection on the Neo4j graph to aggregate global credit exposure, ultimate parent controllers, and sanctions across entire corporate clusters.
Agent-to-Agent Graph JSON Exchange Protocol (/api/agent/graph-subcall):
Specialized agents (e.g. Orchestrator, KYC Agent, Risk Agent, Investigation Agent) pass structured JSON node/relationship payloads to each other over standardized APIs.
Enables downstream agents to run graph algorithms (centrality, PageRank, UBO path tracing) and dynamically render visual graph canvases inside the agentic workspace.
Zero-Trust Purpose-Bound Policy Engine:
Enforces field-level access controls and dynamic redaction based on user role and regional regulations (e.g. redacting raw source documents for RMs while granting full access to Compliance Investigators).
2. The Role of Neo4j & Node/Relationship Schema
Neo4j acts as the Property Graph Backbone, supporting variable-depth ownership traversal, pattern matching, cyclic entity loops, and sanctions path tracing.
Node Labels & Properties
:Organization: id, canonicalName, registrationNumber, lei, jurisdiction, status, communityId, creditExposureUsd
:Person: id, name, nationality, pepHit, isUltimateParent
:SanctionList: id, matchedName, listName, authority, dateListed
:Document: id, sourceSystem, docHash, attribution
Relationship Types & Attributes
:OWNS: ownershipPercentage (float), startDate, sourceRef, confidence
:DIRECTS: appointmentDate, role ('Director', 'Managing Director'), sourceRef
:SUBSIDIARY_OF: controlPct, jurisdiction, ACRAVerified (boolean)
:BENEFICIAL_OWNER: effectiveOwnershipPct, calculatedVia ('GraphTraversal'), auditId
3. Concrete Sample Cypher Queries
Query A: Variable-Depth UBO Traversal (1 to 5 Hops)
code
Cypher

RETURN p.name AS UBO_Name, 
       p.nationality AS Nationality, 
       reduce(pct = 100.0, rel IN r | pct * (rel.ownershipPercentage/100.0)) AS EffectiveOwnershipPct,

code
Cypher
MATCH path = (target:Organization {id: "ENT-SG-1002"})-[*1..4]-(s:SanctionList)

       s.matchedName AS SanctionedParty,
       s.listName AS SanctionAuthority,
       length(path) AS SeparationHops,

Query C: Leiden Community Corporate Group Risk Aggregation
code
Cypher
MATCH (o:Organization {id: "ENT-SG-1002"})
MATCH (cluster:Organization)-[:SUBSIDIARY_OF|OWNS*0..3]-(o)
WITH cluster.communityId AS CommunityID, collect(cluster) AS GroupEntities
RETURN CommunityID,
       size(GroupEntities) AS TotalMemberCount,
       sum(GroupEntities.creditExposureUsd) AS TotalGroupExposureUSD,

Do you need agentic AI for this?

Not for the value. The deck's own economics say so: the KYC analyst's 30–60 minutes, the credit officer's half day — that time goes to reconciliation, and reconciliation is a deterministic problem. Resolve the entity once, publish the pack, monitor for change, and the half day collapses whether or not an agent is involved.

Agents earn their place in exactly three spots: multi-hop investigation where the next query depends on what the last one returned, disambiguation dialogue in the review band, and natural-language access so a credit officer doesn't need to know which of five APIs to call. That's an interface, not an engine.

So the build puts the model here and nowhere else:

Stage	Decides
Normalize, block, candidate-generate	Code
Deterministic rules, probabilistic score, threshold decision	Versioned scorecard — no model
Explanation	Generated from the feature vector
Narration, intent routing	Model, authoritative: false, allowlist-validated
Entitlement / limit / status change	Human or policy — never a model

With EIQ_LLM_PROVIDER=none (default) everything still works. That's the proof the agent layer is optional rather than load-bearing — and it's the slide you want in front of second line.

Why many teams have failed at this

Everyone builds normalize → block → score → link → products → agents. It fails review for three reasons, and the code is organised around those three:

The score can't be defended. A model somewhere produced a number nobody can reproduce a year later. Here every decision stores its full feature vector, rules fired, and scorecard version, in a bitemporal ledger. Nothing is updated in place — a steward override supersedes the engine row, both survive. Any product takes ?as_of= and reconstructs what the bank knew on that date. That's the actual regulator question: why did you onboard this entity in March?

Absence and evidence serialize identically. "No adverse media found" and "adverse media never checked" look the same in JSON, and an agent reports the first. So every product computes evidence sufficiency and abstains below the floor — answerable: false, null payload, machine-readable remediation. The UBO product does the same on a circular nominee holding: a human must confirm the ultimate parent, not a fabricated percentage. This is the single property that makes the products safe to hand to an autonomous consumer, and it belongs in the data layer, not a prompt.

Thresholds can never move. Nobody can say what 0.92 → 0.88 would do, so it stays at 0.92 forever. Because feature vectors are stored, /v1/resolution/replay re-derives the entire book under a hypothetical scorecard — every link that would move, which direction, with its explanation — without re-fetching a single source record. A threshold change becomes a reviewable diff.

Three more that are cheap to build and hard to argue with: evidence is an append-only hash chain with a verify endpoint (an auditor checks a bundle without trusting your database); policy runs at serialization, field by field, returning a SHA-256 receipt of what was withheld under which rule — so "the RM never saw the source document" is provable, not aspirational; and deltas carry materiality → impact → autonomy (automate / client_confirm / human_decision), which is your Prism governance model enforced in code rather than in a diagram.

Agent-facing endpoints

Three doors, one core, identical policy on all of them — an agent cannot reach anything a service couldn't.

REST for services, OpenAPI at /docs
MCP at POST /mcp — tool descriptions written for a model, stating the abstention contract explicitly
A2A — card at /.well-known/agent.json advertising "abstains": true; an unanswerable task returns state input-required with what to acquire

Agents run on rails: per-agent tool allowlists, a runtime guardrail that stops on abstention instead of letting the agent narrate around a gap, and a full trace with the evidence head at call time.

The seeded book is built on the hard cases, not the happy path — an ambiguous top-two forced to review, a circular shareholding, an entity with no screening evidence, a Swiss record blocked for the RM by jurisdiction control, and a registry refresh that dissolves an entity mid-stream.

One thing I'd flag: hybrid retrieval is partially there — graph traversal and keyword paths are implemented, vector search is a documented seam rather than working code. If the MT deck leans on GraphRAG, that's the gap to close first. The Neo4j swap is a cleaner lift: GraphStore has five methods and no caller touches SQL.

3. Concrete Sample Cypher Queries
Query A: Variable-Depth UBO Traversal (1 to 5 Hops)
code
Cypher
MATCH path = (p:Person)-[r:OWNS|BENEFICIAL_OWNER*1..5]->(o:Organization {id: "ENT-SG-1002"})
WHERE r.ownershipPercentage >= 25 OR p.isUltimateParent = true
RETURN p.name AS UBO_Name, 
       p.nationality AS Nationality, 
       reduce(pct = 100.0, rel IN r | pct * (rel.ownershipPercentage/100.0)) AS EffectiveOwnershipPct,
       [node IN nodes(path) | node.canonicalName] AS OwnershipChain;
Query B: Multi-Hop Sanctions & PEP Trace
code
Cypher
MATCH path = (target:Organization {id: "ENT-SG-1002"})-[*1..4]-(s:SanctionList)
RETURN target.canonicalName AS TargetEntity,
       s.matchedName AS SanctionedParty,
       s.listName AS SanctionAuthority,
       length(path) AS SeparationHops,
       [rel IN relationships(path) | type(rel)] AS RelationshipTypes;
Query C: Leiden Community Corporate Group Risk Aggregation
code
Cypher
MATCH (o:Organization {id: "ENT-SG-1002"})
MATCH (cluster:Organization)-[:SUBSIDIARY_OF|OWNS*0..3]-(o)
WITH cluster.communityId AS CommunityID, collect(cluster) AS GroupEntities
RETURN CommunityID,
       size(GroupEntities) AS TotalMemberCount,
       sum(GroupEntities.creditExposureUsd) AS TotalGroupExposureUSD,
       any(e IN GroupEntities WHERE e.sanctionHit = true) AS GroupHasSanctionHit;
